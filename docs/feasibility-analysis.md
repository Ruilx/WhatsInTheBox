## 1. 产品目标复述

**痛点**：用户在搬家/运输封箱后到达新环境时，往往忘记每个箱子里装了什么；需要快速定位某件物品在哪只箱子，并准确打开对应箱子。

**解决方案**：在封箱（放入物品）时，提前在平台录入「活动（一次搬家）→ 箱子 → 物品」的层级信息，并给每个箱子分配唯一编号（大写字母 + 两位数字，如 `A01`）。到达新环境后，用户可通过列表浏览、关键字搜索，或**扫描贴在箱子上的二维码**三种方式，快速定位物品及其所在箱子的位置。

**目标用户**：以个人或家庭为主的搬家/运输场景使用者；也可能扩展到小团队物资管理。核心使用者是「封箱时录入信息的人」与「到货后查找物品的人」（常为同一人，也可能多人共享同一系统）。系统定位为轻量级、单机/小团队自用后台，而非多租户 SaaS。

## 3. 技术栈可行性评估（逐条 + 与常识冲突/需查证点）

### 3.1 前端：Vue3 + Vite + TypeScript + npm + ant-design-vue
- **可行性**：高。Vue3（稳定版）、Vite（主流构建）、TypeScript（强类型利于中后台）、ant-design-vue（组件齐全、与 antd 设计体系一致）均为成熟稳定选型，符合「稳定版本、不盲目追新」。
- **风险点**：
  - **ant-design-vue 是桌面优先组件库**（已查证：其栅格/表单/表格默认按 PC 尺寸设计，移动端会出现按钮过小、表格溢出、触控区不足等问题）。需额外做响应式适配（viewport、媒体查询、`flex-wrap`、隐藏次要列、增大触控区）。
  - 移动端扫码需引入相机解码库（如 `html5-qrcode` / `@zxing/browser`）或依赖系统/微信扫一扫，需明确（见开放问题）。
- **需用户查证**：是否接受 ant-design-vue 在移动端需额外适配的工作量；或是否考虑移动端单独用 Vant 等移动端库（但这与「统一用 ant-design-vue」冲突，需拍板）。

### 3.2 后端：Python 3.12 + FastAPI + venv + pip + pymysql
- **可行性**：高。Python 3.12 为稳定版（2023-10 发布），FastAPI + Pydantic v2 已良好支持 3.12。
- **⚠️ 关键冲突/风险（已查证）**：**pymysql 是同步（阻塞）驱动**。若在 `async def` 路由中直接调用 pymysql，会阻塞 FastAPI 单线程事件循环，导致所有并发请求退化为串行、高并发下严重掉性能。
  - **缓解（必须遵守其一）**：① 数据库访问相关路由统一用普通 `def`（FastAPI 会自动丢进线程池执行，不阻塞事件循环）；或 ② 用 `asyncio.to_thread()` / `anyio.to_thread.run_sync()` 包裹同步 DB 调用；③ 多 Worker（Gunicorn/uvicorn workers）部署分摊。原型未提及此点，**强烈建议用户在架构阶段明确该约束**。
  - 若未来想彻底解耦，可考虑 `aiomysql`/`asyncmy`（异步驱动），但与原型「使用 pymysql」冲突，需用户决定。

### 3.3 路由格式 `module_name/controller_name/action_name`，`module_name` 固定 `whatsinthebox`
- **可行性**：高。FastAPI 支持任意路径前缀与路径参数；固定前缀便于 nginx 反向代理与前端路由统一。
- **注意**：与前端「短 URL（固定前缀 + 名称）」如何衔接需要约定（见开放问题），避免前后端路由风格割裂。

### 3.4 无 ORM，手写参数化 SQL（`where id=?`，禁止字符串拼接）
- **可行性**：高，且对防 SQL 注入正确。
- **风险**：开发效率较低、字段多易出错、分页/动态筛选拼接需谨慎。建议封装统一的数据访问层（DAL），集中管理参数化查询模板（符合「数据/业务分层」要求）。

### 3.5 不使用 Redis 缓存
- **可行性**：高（数据量小，家庭/小团队级，无性能压力）。
- **连带影响**：登录态/session **无法放 Redis**，必须落在内存或数据库（见 3.9 与风险章节）。

### 3.6 数据/业务分层代码结构
- **可行性**：高，清晰解耦，符合「代码架构分明、功能解耦」要求。

### 3.7 存储：MySQL + 惰性连接 + 连接池 + `.env`（不入库）+ `.env.example`
- **可行性**：高。
- **⚠️ 需查证**：
  - **pymysql 本身不带连接池**，需借助 `DBUtils.PooledDB` 或自实现池；原型说「连接池」但未指定实现，**需明确**。
  - 惰性连接（lazy connect）+ 连接池 + 断线重连（`ping(reconnect=True)`）需在 DAL 中处理。
  - 字符集/排序规则未定，中文必须 `utf8mb4`（如 `utf8mb4_general_ci` 或 `utf8mb4_unicode_ci`），**需用户确认**。

### 3.8 前后端代码目录分开、分别启动
- **可行性**：高。常规前后端分离部署，nginx 反代后端 API + 前端静态资源/前端开发服务器。

### 3.9 登录：加盐 hash cookie + 多端登录（无注册）
- **可行性**：可行，但**安全与存储方案是核心待定点**。
  - 关键问题：cookie 里存什么？若直接存「用户名+弱 hash」易被伪造；推荐方案是 cookie 存**随机 session token**，服务端校验（token 由服务端用密钥 + 盐做 HMAC 或随机生成并落库）。
  - **多端登录**意味着 session 需支持同一用户多 token；在「无 Redis」前提下，session 应落到 **MySQL 的 session 表**（否则多实例/重启即失效）。
  - 需明确：cookie 字段名、是否 `HttpOnly`/`Secure`/`SameSite`、有效期、登出/过期/踢下线机制。

### 3.10 nginx 反向代理固定前缀 + 二维码扫码
- **可行性**：高。nginx `location /前缀/` 反代后端；前端路由用 History 模式需 nginx 配置 fallback。
- **⚠️ 需查证**：二维码内容是「短 URL 本身」还是「箱子编号」？由谁生成（后端导出图片？用户自己用 URL 生成？）？「手工输入二维码」的真实含义需澄清（见开放问题）。

## 4. 风险与缓解

| # | 风险 | 等级 | 缓解建议 |
|---|---|---|---|
| R1 | pymysql 同步阻塞 FastAPI 事件循环 | 高 | 路由用 `def` 或 `asyncio.to_thread` 包裹；多 Worker 部署；统一 DAL 封装 |
| R2 | 加盐 hash cookie 方案不清，存在伪造/会话固定风险 | 高 | cookie 存随机 session token + 服务端校验；session 落 MySQL 表；设 `HttpOnly/Secure/SameSite`、有效期 |
| R3 | 多端登录在无 Redis 下如何共享会话 | 中 | session 入库（token 表），支持多 token；或暂限定单实例部署 |
| R4 | 二维码内容与生成方不明 | 中 | 明确内容（短 URL / 编号）、生成入口（后端导出 PNG / 仅给 URL 让用户自印） |
| R5 | 短 URL 用「活动名/箱子名」，含中文/空格/特殊字符 + 重名冲突 | 中 | 定义 URL 编码与 slug 规则、大小写处理、跨活动重名冲突处理；名称编辑后旧二维码失效策略 |
| R6 | 照片/缩略图存储位置未定义 | 中 | 明确 blob / 本地目录 / 对象存储；建议本地目录 + URL 访问（或对象存储），不推荐大 blob |
| R7 | ant-design-vue 移动端适配不足 | 中 | 统一做 viewport + 响应式断点 + 触控区放大 + 表格列隐藏；必要时关键页定制 |
| R8 | 逻辑删除（soft delete）与「同活动箱子名不重复」唯一约束冲突 | 中 | 唯一约束放应用层或在唯一索引包含 `deleted` 维度；明确删除后名字可否重用 |
| R9 | 日志表、联合物品枚举、各状态枚举未定义 | 中 | 补字段/枚举清单（见开放问题） |
| R10 | 单实例 vs 多实例部署未定，影响 session 与连接池 | 低 | 明确部署形态；多实例必须 session 落库 + 连接池按实例配置 |
| R11 | 数据量虽小但无备份策略 | 低 | 约定 MySQL 定时备份（mysqldump/cron） |

## 6. 用户故事（搬家用户视角）

1. **录入封箱信息**：作为一名正在搬家打包的用户，我希望在封箱时给每个箱子贴唯一编号并录入箱子与物品信息，以便到新家后不会忘记里面装了什么。
2. **扫码快速定位**：作为一名到达新家的用户，我希望用手机扫描箱子上的二维码（或输入短 URL）直接打开该箱子页面，以便快速确认里面有什么、是否含我要找的物品。
3. **关键字搜索**：作为一名想找某件特定物品（如「螺丝刀」）的用户，我希望通过搜索框按名称/描述/备注模糊查找，以便跨箱子定位它所在的箱子。
4. **折叠空箱**：作为一名整理完物品的用户，我希望把已清空的箱子标记为「折叠」，以便区分哪些箱子还能再用、哪些已收起。
5. **关联套装**：作为一名管理成套设备（如「相机 + 镜头 + 三脚架」）的用户，我希望把它们关联为联合物品，以便一次检索就能看到整套的位置与组成。

## 7. UI 设计要点（基于「页面风格」归纳）

- **风格基调**：「普通 / 原生样式」为主，不追求花哨视觉；控件语义清晰。
- **主题**：根据系统深浅色自动切换，并支持用户手动指定深浅主题。
- **字体**：黑体（如系统无衬线黑体栈），必须正确渲染中文。
- **动效**：部分过渡动效（高亮呼吸提示、控件淡入淡出），页面左右保留合适 `margin`，避免内容贴边。
- **按钮**：语义极清晰的操作用 icon/图片代替文字；普通态与 `hover` 态亮度不同，明确可交互。
- **硬约束**：**禁止使用任何 emoji 图标**（icon 用 SVG/图片，不用 emoji 字符）。
- **移动端**：布局需响应式，触控目标足够大，表格在窄屏隐藏次要列、操作更易点按。

## 8. ⚠️ 待用户澄清的开放问题清单（最重要）

> 说明：以下均为需求不清、边界缺失或需用户拍板的事项；我只列问题并给「初步建议」（仅供参考，不代替决定）。请勿让我猜测。

### A. 账号与登录安全
- **A1 登录账号如何创建/下发？初始管理员账号从哪来？**
  - 为什么：原型明确「无注册界面」，但没说账号怎么产生（手动写库？后台脚本？首个访问者自动成为管理员？）。
  - 初步建议：提供一个一次性初始化脚本/接口创建首个管理员；或约定由部署者手动向 `user` 表插入。
- **A2 加盐 hash cookie 的具体方案？**
  - 为什么：涉及安全。需明确 hash 算法、盐的来源与存储、cookie 字段名、是否 `HttpOnly/Secure/SameSite`、有效期、刷新策略。
  - 初步建议：cookie 存随机 session token，服务端用密钥做 HMAC 签名防篡改；`HttpOnly+Secure+SameSite=Lax`；有效期可设 7~30 天。
- **A3 多端登录如何识别与管理？**
  - 为什么：「可多端登录」意味着同一用户可有多个有效会话；需定义是否允许查看/踢出其他设备、上限多少。
  - 初步建议：session 落 MySQL `session` 表，每端一条记录，支持多 token；暂不强制设备上限。
- **A4 登出 / 忘记退出 / 会话过期如何处理？**
  - 为什么：关系到安全与实现。需明确主动登出、超时过期、服务端能否强制失效。
  - 初步建议：登出即删除该 session 记录；超时（如 30 天无活动）自动失效。

### B. 二维码与 URL 路由
- **B1 二维码内容到底是什么？**
  - 为什么：可能是「短 URL 本身」或「箱子编号」。两者实现与用户体验完全不同。
  - 初步建议：二维码内容 = 短 URL（如 `/wb/活动名/箱子名`），扫码即跳转，最符合「印到箱子上、手工输入」的描述。
- **B2 二维码由谁生成？系统是否要提供「生成/下载二维码图片」功能？**
  - 为什么：原型说「需要手工输入二维码」，含义模糊——是用户自己拿 URL 去生成二维码，还是系统导出 PNG 供打印？
  - 初步建议：系统提供「查看/下载该箱子/活动二维码 PNG」入口，内容即短 URL；用户自行打印粘贴。
- **B3 固定前缀用哪个字符串？**
  - 为什么：原型让我「起一个」，需用户最终确认（工程名 `whatsinthebox` 还是更短如 `wb`）。
  - 初步建议：用简短前缀如 `wb`（whatsinthebox 缩写），兼顾可读与输入成本。
- **B4 活动名合并为前缀的方案是否采用？**
  - 为什么：原型给出「把活动名当前缀，URL 更短」的备选；影响 nginx 配置与路由设计。
  - 初步建议：默认用固定前缀 `wb`，活动名作为路径段；合并方案可作为可选高级配置。
- **B5 活动名/箱子名含中文、空格、特殊字符时，URL 如何编码与解析？大小写是否敏感？**
  - 为什么：短 URL 以名称为主，中文需 URL 编码；nginx 与前端路由需一致解析；大小写可能影响唯一性。
  - 初步建议：统一 `encodeURIComponent`；服务端解码；名称比较大小写不敏感或统一转小写建索引。
- **B6 跨活动同名箱子，URL（活动名/箱子名）是否冲突？**
  - 为什么：URL 不含活动 ID，仅用名称；不同活动下箱子名可能相同，导致 URL 歧义。
  - 初步建议：URL 必须带活动名段（已定），且「同活动下箱子名不重复」已约定；跨活动天然隔离。需确认是否允许跨活动重名。
- **B7 箱子/活动名称被编辑后，旧二维码/旧 URL 是否失效？是否需要别名/重定向？**
  - 为什么：名称可变，印在箱子上的二维码若失效会造成「扫码打不开」。
  - 初步建议：二维码绑定「箱子唯一编号」而非名称；URL 优先用编号或保留别名映射，保证旧码可用。

### C. 数据存储与文件
- **C1 照片/缩略图存哪里？**
  - 为什么：原型列了 `photo`/`thumb` 但没说存储方式（MySQL blob / 本地目录 / 对象存储）。
  - 初步建议：存本地目录（如 `uploads/`）+ 数据库仅存路径/URL；不推荐大 blob 入表；缩略图后端生成。
- **C2 文件上传接口、大小/格式限制、访问鉴权？**
  - 为什么：需定义上传入口、是否登录后可传、最大体积、允许类型（jpg/png）、缩略图尺寸。
  - 初步建议：登录后可传；限制单文件 ≤ 5MB、类型 jpg/png；缩略图 ≤ 300px。
- **C3 数据库字符集/排序规则？**
  - 为什么：中文必须 `utf8mb4`，否则生僻字/emoji 会出错（且本系统禁 emoji 但用户备注可能含特殊字符）。
  - 初步建议：库/表统一 `utf8mb4` + `utf8mb4_general_ci`（或 `unicode_ci`）。
- **C4 数据库连接池实现选型？**
  - 为什么：pymysql 无内置连接池，需明确（DBUtils.PooledDB 等）。
  - 初步建议：用 `DBUtils.PooledDB` 包裹 pymysql，配置最小/最大连接数。

### D. 数据模型与字段细节
- **D1 日志表字段结构未定义。**
  - 为什么：原型仅说「比如查询记录、物品放置、取出等」，缺具体字段。
  - 初步建议：至少含 `id, user_id, action_type, target_type, target_id, detail, ip, create_time`，并带统一 `deleted/create_time/update_time`。
- **D2 各状态枚举值范围？**
  - 为什么：箱子状态（打开/折叠/损伤/淘汰…）、物品状态（已取出…）、活动状态（开始/停止…）、联合物品状态（正常/失效…）需明确完整枚举，否则筛选与展示无依据。
  - 初步建议：用户给出每类状态的完整枚举清单；可配置字典表。
- **D3 联合物品「物品联合方式」枚举值？**
  - 为什么：原型示例「原装/补配/已替代」，是否还有更多（如「替代」「可选」）？
  - 初步建议：用户确认最终枚举集；预留扩展。
- **D4 type 字段（箱子/物品/活动/联合物品类型）是自由文本还是字典枚举？**
  - 为什么：影响筛选器呈现与数据规范性。
  - 初步建议：用可配置字典（如箱子类型：纸箱/塑料箱/木箱…），下拉选择而非自由输入。
- **D5 箱子编号规则：大写字母+两位数字（A01…Z99）是全局唯一还是活动内唯一？谁生成？容量够吗？**
  - 为什么：26×100=2600 个编号；需明确唯一范围与生成方式（系统自动 or 用户录入）。`serial_no` 是用户录入的串号，与编号是否同一概念需分清。
  - 初步建议：编号由系统按活动内自增/规则生成且活动内唯一；`serial_no` 为用户的额外串号，二者区分。
- **D6 逻辑删除 + 「同活动箱子名不重复」唯一约束冲突如何处理？**
  - 为什么：软删除后同名记录仍在，唯一索引会阻止新建同名；需定义删除后名字可否重用。
  - 初步建议：唯一约束放应用层校验，或唯一索引包含 `deleted` 维度；删除后允许重用名称。

### E. 权限、多用户与部署
- **E1 权限模型：是否只有单一管理员角色？**
  - 为什么：原型未提多角色；若家庭/小团队多人使用，可能需「只读/编辑/管理员」分级。
  - 初步建议：MVP 先单一管理员；若有多人需求，后续加角色字段。
- **E2 是否支持多用户共用系统？**
  - 为什么：原型偏向单人自用；但「多端登录」暗示可能多人。需明确数据是否按用户隔离。
  - 初步建议：MVP 单用户/单管理员；多人共享同一数据集（家庭场景）先不做隔离。
- **E3 部署形态：单实例还是多实例？**
  - 为什么：影响 session 存储（无 Redis 时多实例必须 session 落库）与连接池配置。
  - 初步建议：MVP 单实例（uvicorn/Gunicorn 单节点）；多实例需 session 落库。

### F. 业务逻辑边界
- **F1 「空箱子」的判定标准？**
  - 为什么：折叠仅在「空箱子」允许；空=无物品，还是无「未取出」物品（取出后仍算有物品记录）？
  - 初步建议：空=该箱子下无 `status=未取出` 的物品（已取出不计入）。
- **F2 活动「停止」后，箱子/物品还能编辑吗？**
  - 为什么：开始/停止状态是否约束子资源操作需明确。
  - 初步建议：停止后只读/禁止新增，已有数据可查看；或仅禁止结构变更。
- **F3 箱子嵌套（parent_box_id）层级是否有限？移动端如何展示层级？**
  - 为什么：父箱子可无限嵌套，需定义层级深度与 UI 呈现（面包屑/树）。
  - 初步建议：不限层级但 UI 用面包屑+列表，避免深层嵌套复杂度。
- **F4 取出/删除操作的级联影响？**
  - 为什么：删除箱子时其下物品如何处理（禁止/级联软删/提示）需定义。
  - 初步建议：删除箱子前校验无未取出物品；或级联软删并提示。

### G. 其他
- **G1 搜索/筛选是后端 SQL 支持还是前端内存过滤？**
  - 为什么：每页 50 条、数据量小，但「跨页搜索」与否决定实现方式。
  - 初步建议：后端 SQL `LIKE` + 参数化，支持跨页全局搜索（更安全、正确）。
- **G2 是否需要数据备份与恢复机制？**
  - 为什么：家庭重要物资数据丢失成本高。
  - 初步建议：约定 MySQL 定时备份（cron + mysqldump）。
- **G3 时间展示：统一 Asia/Shanghai 还是允许用户本地时区？**
  - 为什么：原型定库时区为 `Asia/Shanghai`；前端展示格式/时区需明确。
  - 初步建议：存储统一 `Asia/Shanghai`；前端按用户偏好展示（默认上海时区）。
- **G4 是否需要「忘记密码 / 修改密码」功能？**
  - 为什么：无注册但管理员可能需改密。
  - 初步建议：提供登录后的「修改密码」；忘记密码走初始化脚本重置。
